# 캔버스 프레임 최적화 (2026-11-16)

## 확인한 원인과 수정

- 숨긴 객체 관리, 표시 여부·고급 스타일 검사, 애니메이션 예약 검사, 구형 노트북 변환이 작은 수정에도 전체 객체를 순회했다. `ItemSubset`으로 불변 스냅샷의 변경 ID만 검사하고 관련 객체 집합을 재사용한다. 관계없는 스냅샷으로 전환하면 안전하게 다시 구축한다.
- Canvas2D의 부분 갱신도 모든 래스터 레코드를 검사했다. `RasterPaintIndex`는 회전·그림자를 포함한 실제 그리기 영역을 RBush로 검색한다. 검색 결과는 기존 그리기 순서대로 정렬하며, 전체 화면이 겹치는 경우에는 기존 순서를 재사용한다. 삭제·숨김·이동·깊이 변경에도 인덱스를 갱신한다.
- 구조 공유 스냅샷의 256개 해시 버킷은 큰 캔버스에서 작은 수정에도 많은 레코드를 복사했다. 1024개로 나눠 복사량을 줄였다.
- 10만 개 일반 코드 데이터에서 초기 공동 편집 문서의 다중 복제로 Automerge WASM 메모리 소진이 재현됐다. 서버 동기화 뷰에서 CRDT 스냅샷이 없는 일반 데이터는 필요할 때 문서를 구성한다. 기존 CRDT 스냅샷이 있는 데이터의 복원·병합은 유지한다. 따라서 모든 CRDT 이력 규모의 메모리 한계를 해결했다는 의미는 아니다.

## 측정

실제 Chrome, 개발 빌드, 2100×1450, 모의 브로커로 테스트했다. 운영 캔버스 데이터는 수정하지 않았다. 코드 객체 전체가 화면에 포함되지만, 작은 객체는 기존 품질 설정에 따른 개요 렌더링을 사용한다. 모든 코드 편집기·영상이 동시에 활성화된 부하는 아니다.

| 조건 | 확대·축소 | 1천 개 추가 붙여넣기 | 붙여넣기 소요 시간 |
|---|---:|---:|---:|
| 수정 전 1만 코드 객체 | 59.3 FPS | 44.4 FPS | 2005ms |
| 최종 수정 후 10만 코드 객체 | 59.5 FPS | 51.5 FPS | 1436ms |

최종 10만 개 측정에서 확대·축소 프레임 간격 p95는 16.8ms, 붙여넣기 p95도 16.8ms, 붙여넣기 최대 간격은 50ms였다. 붙여넣기는 실제 여러 프레임에 걸쳐 점진적으로 표시됐고 브라우저 예외는 없었다. 서로 객체 수가 다른 두 행은 동일 부하의 개선율로 해석하면 안 된다. 하드웨어·브라우저·객체 구성에 따라 결과는 달라지며 항상 60FPS를 보장하지 않는다.

10만 개 레코드의 작은 변경 영역 검색 별도 측정(500회): 전체 순회 324.6ms → 인덱스 검색 3.26ms, 후보 36개. 이는 검색 단계만의 수치이며 전체 렌더링 속도 배율이 아니다.
