# 객체 준비 병목 최적화

2026-10-14에 `DepthVectorLayer`의 준비 과정을 수정했습니다. 이전에는 프레임마다 전체 객체 목록을 다시 열거하고, 이미 준비한 앞부분까지 반복 처리했습니다. 목록 열거와 순회가 8ms 예산을 소진하여 한 프레임에 신규 객체가 거의 하나씩만 준비되는 병목이 있었습니다.

`ScenePreparationQueue`는 불변 객체 사전이 바뀔 때 한 번 목록을 생성합니다. 이후에는 커서를 저장하고 다음 프레임에서 이어서 처리합니다. 목록 생성 시간과 청크 처리 예산을 분리하고, 각 청크의 방문 작업을 8ms로 나눕니다. 이는 목록 생성·GPU 그리기 등을 포함한 전체 프레임 시간이 8ms라는 의미는 아닙니다.

부분 준비 중에도 원래 인덱스를 사용하여 CPU·GPU의 표시 순서를 유지합니다. 기존 자원을 재사용하고, 삭제되거나 벡터 표시 대상에서 제외된 객체를 제거합니다. 장면·폰트·라우팅 등의 입력이 바뀌면 최신 장면으로 작업을 교체하며, 움직임이 멈춘 뒤 필요한 해상도 갱신도 동일한 준비 큐로 처리합니다. 카메라만 바뀌는 준비 완료 장면에서는 캐시를 사용합니다.

## 실제 GPU에서 모든 객체가 화면 안에 있는 장면

NVIDIA RTX 3060 Ti, Chrome 155, 1800×1100, DPR 1에서 동일한 밀집 도형 배치로 측정했습니다. 이전 측정은 [수십만 객체 검증](hundred-thousand-canvas-performance.md)에 보존했습니다. 아래는 로컬 프로덕션 빌드 검증 결과입니다. 준비 완료는 `preparing=false`와 실제 렌더링 객체 수가 전체 개수에 도달했는지 함께 확인했습니다.

| 화면 안 객체 수 | 수정 전 | 수정 후 로딩·전체 준비 | 이동 평균 FPS | 확대·축소 평균 FPS | 확대·축소 95백분위 |
| --- | --- | ---: | ---: | ---: | ---: |
| 100,000 | 120초 안에 준비 미완료 | 5.47초 | 59.98 | 58.06 | 32.3ms |
| 200,000 | 120초 안에 준비 미완료 | 8.88초 | 58.06 | 50.42 | 61.8ms |
| 500,000 | 120초 안에 준비 미완료 | 25.03초 | 53.81 | 43.59 | 103.3ms |

50만 개도 모델 개수뿐 아니라 실제 준비된 렌더링 객체 수가 500,000에 도달했습니다. 약 20.6초 시점에는 411,784개가 준비됐고, 약 25초에 모두 준비됐습니다. 해당 실행의 목록 생성은 장면 입력 변경에 따른 3회였으며, 준비 청크를 처리하는 매 프레임마다 목록을 재생성하지 않았습니다. 같은 불변 사전에 대한 단위 검증에서는 10만 개를 나눠 처리하는 동안 목록 열거가 정확히 한 번 발생했습니다.

준비 완료 이후의 이동·확대·축소는 각각 300 프레임을 측정했습니다. 모든 객체를 매 프레임 처리할 필요가 있는 밀집 장면에서는 여전히 지연 프레임이 있습니다. 특히 50만 개 확대·축소의 최대 프레임 시간은 186.2ms였으므로, 평균 FPS가 30을 넘는 것과 모든 프레임에서 30 FPS를 방어하는 것은 다릅니다. 이번 변경은 준비가 끝까지 진행되지 않던 병목을 해결했으며, 밀집 장면의 전체 상호작용 지연까지 해결했다고 판정하지 않습니다.

텍스처를 공유하는 불투명 사각형, 테두리·그림자 없음이라는 장면 조건은 이전 테스트와 같습니다. 복잡한 텍스트·이미지·손그림 및 대규모 동시 편집 성능을 보장하는 결과는 아닙니다. 로딩·준비 시간에는 테스트 데이터 생성과 프런트엔드 초기화가 포함되지만, 실제 서버에서 수십만 객체를 내려받는 네트워크 처리량은 포함되지 않습니다.

## 기능 검증

Node 테스트 93개를 통과했습니다. 추가 테스트는 10만 객체에서 목록을 한 번만 열거하는지, 청크가 이미 처리한 앞부분을 다시 방문하지 않는지, 준비 도중 장면 교체 시 오래된 작업을 버리는지, 품질 갱신에서 목록을 재생성하지 않는지와 비싼 작업의 진행 여부를 검증합니다.

실제 GPU 브라우저에서 텍스트·코드·메모 편집과 저장·재접속, 깊이 선택, 객체 이동·모서리 크기 조절, 드로잉·그림체 화살표 선택을 확인했습니다. GPU 컨텍스트를 잃으면 Worker 기반 CPU 화면으로 복원됐으며, GPU와 Worker의 세 위치 픽셀 색상은 원래 객체 채우기 값과 일치했습니다. CPU에서 이동·회전·그림자를 수정한 뒤 부분 갱신 결과와 전체 다시 그리기의 픽셀 차이는 0이었습니다.

[측정 결과 및 렌더러 통계](canvas-preparation-benchmark.json)에 전체 준비 여부, 커서 진행량, GPU 어댑터와 프레임 지연을 기록합니다. 재현은 [브라우저 측정 스크립트](../scripts/benchmark-large-canvas-browser.mjs)를 사용합니다. `BENCHMARK_ASSET_ORIGIN`을 지정하면 API와 실시간 연결은 실제 서비스에 유지하면서 해당 주소의 정적 프런트엔드 빌드로 검증할 수 있습니다.

## Project Orchestra 배포 후 확인

Project Orchestra의 정적 프런트엔드 빌드·내보내기로 배포했습니다. 실제 서비스의 정적 파일을 사용하는 테스트에서도 모든 객체가 화면 안에 있는 장면의 준비를 완료했습니다.

| 객체 수 | 로딩·전체 준비 | 이동 평균 FPS | 확대·축소 평균 FPS | 확대·축소 95백분위 | 확대·축소 최대 지연 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100,000 | 6.05초 | 60.00 | 58.63 | 33.1ms | 59.1ms |
| 200,000 | 9.66초 | 58.39 | 50.70 | 61.7ms | 121.6ms |
| 500,000 | 25.27초 | 50.99 | 41.43 | 136.8ms | 200.2ms |

준비 완료 이후의 평균 FPS는 모두 30을 넘었지만, 느린 프레임이 있으므로 모든 프레임에서 30 FPS를 보장하는 결과는 아닙니다. 위 지연 수치는 준비 중인 부분 장면이 아니라 전체 객체가 실제 준비된 이후의 측정입니다.

배포 후에도 실제 서비스의 텍스트·코드·메모 저장·재접속, 깊이 선택, 이동·모서리 크기 변경 및 드로잉·그림체 화살표 선택을 다시 확인했습니다.

검증에 사용한 임시 캔버스는 삭제하고 로컬 검증 서버도 종료했습니다.
