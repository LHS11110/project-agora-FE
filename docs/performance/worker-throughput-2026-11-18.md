# Worker 새 프레임 처리량 개선

## 확인된 원인

`ec53793`에서는 카메라가 움직여도 기존 Worker 이미지가 화면을 덮고 있으면 CSS 재투영으로 처리했다. 이 경우 화면은 약 60 FPS여도 새 Worker 프레임 카운터는 0에 가까웠다. 직접 GPU 렌더 요청을 넣은 동일 엔진은 수정 전에도 약 124~125 FPS를 처리했다. 따라서 처리 엔진이 0→125배 빨라졌다는 의미가 아니다. 이동 중 새 프레임 제출 정책을 수정한 결과다.

## 변경

- `DepthVectorLayer`: 실제 카메라 변경이 있는 동안에는 새 GPU 프레임을 요청한다. 기존 재투영은 Worker 응답을 기다리는 동안 즉각적인 화면 정합을 유지하는 데 사용한다. 정지 화면은 계속 재사용한다.
- 장면·래스터·텍스처 캐시는 유지한다. 기존 60Hz 카메라 검사에서 React commit과 rasterization은 모두 0회로 유지되면서, 새 Worker 프레임은 3초간 0→181회가 됐다.
- `WorkerGpuRenderer.pump`: 텍스처 업로드가 없는 카메라 프레임에서는 빈 `Promise.allSettled([])` 대기를 제거하여 즉시 전달한다. 같은 CSS 크기·transform을 중복 설정하지 않는다.
- `WorkerGpuRenderer.receive`, `gpuRenderer.worker`: 요청·완료·실제 반영·폐기를 구분하고 전달/처리/표시 시간을 수집한다. 최근 샘플은 240개, 진행 중 패킷은 기존처럼 1개로 제한한다. 오래된 장면 프레임은 폐기한다.
- Worker FPS 카운터를 인위적으로 올리지 않고 실제 ImageBitmap을 받아 반영한 횟수를 검증한다. 정지 화면에서 의미 없는 60회 반복 렌더링은 만들지 않는다.

## 실측

Chrome 157.0.8103.78, 하드웨어 GPU, 낮음 품질, 1200×800, 캐시가 준비된 2만/20만 직사각형 객체. 120Hz 타이머를 요청했으며 실제 입력은 약 125Hz였다. 각 동작 4초, 실제 반영 프레임 수/실제 경과 시간으로 계산했다. 이 객체 수는 준비된 GPU 장면의 개수이며 모든 객체가 동시에 화면에 보이는 조건은 아니다. 다양한 코드·이미지·동영상 혼합 장면 전체의 성능 보장은 아니다.

|객체 수|동작|새 Worker FPS 전→후|화면 rAF Hz|프레임 p95 ms|왕복 p95 ms|
|---:|---|---:|---:|---:|---:|
|20,000|pan|0.00 → 124.73|59.99|16.70|1.30|
|20,000|zoom|0.00 → 124.49|60.24|16.80|1.10|
|200,000|pan|0.25 → 124.98|59.99|16.80|1.40|
|200,000|zoom|0.00 → 124.74|60.25|16.70|1.10|

13개 깊이 레이어(각 12개 도형, GPU Worker 4개 + Canvas 2D 9개)를 동시에 갱신하는 별도 테스트에서도 GPU Worker 각각 약 124.74 FPS를 기록했다. 각 Worker의 진행 중 패킷은 1개였으며 합계 FPS를 개별 Worker FPS로 표시하지 않았다.

일반 rAF 기반 60Hz 카메라 테스트에서도 이동·확대/축소 각각 약 60.37회/초의 새 Worker 프레임을 확인했다. 120/144Hz 이상 입력을 지원하는 브라우저에서는 입력이 전달되는 빈도와 GPU 여유에 따라 더 많은 새 프레임을 처리할 수 있다. 앱에서 고정 FPS 상한은 추가하지 않았다.

타이밍은 각 스레드 내부의 wall-clock 경과 시간이다. `submitMs`는 GPU 명령 제출 함수의 CPU 측 경과 시간이며 GPU 타임스탬프 쿼리로 잰 실제 GPU 실행 시간은 아니다.

## 한계와 검증

- 입력·변경이 초당 60회보다 적으면 새 프레임도 그보다 적을 수 있다. 캐시 재사용 중 낮은 Worker FPS는 성능 저하를 뜻하지 않는다.
- 최초 장면 준비, 많은 텍스처 갱신, 높은 해상도·품질, 브라우저/GPU 부하 및 성능이 다른 기기에서 항상 최소 60을 보장하지 않는다. 입력이 충분한 위 측정에서는 모든 조건이 60 FPS를 넘었다.
- Worker 처리율과 화면 표시율은 다른 지표다. 실제 브라우저 주사율에 맞는 화면 rAF는 약 60Hz로 유지됐다.
- 변경 없는 화면은 계속 재사용한다. 단위 테스트에서 응답 후 자동으로 추가 렌더 요청을 만들지 않는지, 대기 패킷 1개·최근 샘플 240개 제한과 폐기 처리를 검증한다.
- GPU Worker/main fallback의 이동·확대/축소 픽셀 정합 및 반투명 텍스처 회귀 테스트가 통과했다.
- 이 변경에서는 진행 중인 다른 성능 모니터/UI 변경 파일을 수정하거나 커밋하지 않았다.

재현:

```bash
AGORA_E2E_ORIGIN=https://127.0.0.1:5195 \
AGORA_E2E_PLAYWRIGHT_MODULE=/path/to/playwright-core/index.mjs \
MIN_WORKER_FPS=60 BENCH_OUTPUT=/tmp/worker-throughput.json \
node tests/performance/worker-throughput.mjs
```
