# 참여자 변경 중 브로커 오류 복구

자동 편집자 접속·퇴장과 기존 참여자의 연속 편집을 함께 실행하면, 전송 중이던 relay가 이미 퇴장한 peer를 가리킬 수 있습니다. 수정 전 100개 객체·7회 접속/퇴장·462회 편집 재현에서 `CANVAS_RELAY_TARGET_INVALID`와 이전 term의 저장을 거절하는 `HOST_FENCED`가 발생했습니다. 기존 RTC 처리기는 전자를 오류 토스트와 전체 소켓 재접속으로 처리해 추가 호스트 변경을 유발했습니다.

`RtcMembershipRecovery`는 다음을 처리합니다.

- relay 대상/호스트 전환 오류는 기존 인증 소켓에서 `rtc_list`로 현재 참여자와 호스트를 재조회합니다. 이미 새 term을 받은 뒤 도착한 이전 term의 거절은 현재 호스트를 중단시키지 않습니다.
- 재조회는 250ms 간격으로 제한하고 전송 예산이 부족하면 재시도합니다. 대기 중 편집과 요청 카운트는 기존 HostCanvasSession이 유지합니다.
- 접근 거절·잘못된 프로토콜·큰 메시지 등 실제 오류는 기존 오류 처리기로 전달합니다. `host_batch_result`의 저장 거절도 기존 저장 fencing 처리기를 유지합니다.

브로커는 이전 term을 대상 목록보다 먼저 확인하고, 거절 응답에 길이가 제한된 `relay_term`·`relay_type`을 포함합니다. 거절된 요청을 적용하거나 권한 검사를 생략하지 않습니다. 레코드 내용이나 인증 토큰은 오류 응답에 추가하지 않습니다.

새로고침으로 캔버스 소켓이 닫히거나 인증 만료로 예정된 재접속을 할 때는 `{:shutdown, reason}`으로 종료합니다. 종료 이유는 유지하면서 정상 제어 흐름을 GenServer 비정상 종료로 기록하지 않습니다. 알 수 없는 종료 이유와 느린 소비자 종료는 기존 비정상 경로를 유지합니다.

검증:

```bash
node --test tests/*.test.js
```

브로커는 Room·권한·상관관계·전송량 제어 테스트와 별도 localhost CA를 사용한 TLS WebSocket 업그레이드/정상 종료 테스트로 확인합니다. C++ fixture 전용 BackendSocket TLS 테스트는 그 fixture의 CA·WSS 대상이 별도로 필요합니다. 실제 배포 검증은 임시 캔버스에서 두 브라우저의 반복 접속/퇴장과 연속 편집, RedisJSON의 최종 좌표·색상, 새 연결의 재로딩을 확인합니다. 기존 사용자 캔버스는 재현용으로 변경하지 않습니다.

## 배포 후 실제 브라우저 결과

100개 객체, 7회 접속/퇴장, 477회 연속 편집에서 브로커 오류 토스트와 JS 예외가 없었습니다. 기존 참여자는 처음 열린 캔버스·협업 WebSocket 2개를 계속 사용했습니다. 이전 term의 요청을 거절한 `HOST_FENCED` 프레임 1건은 정상 복구했고 실제 쓰기로 적용하지 않았습니다. 최종 좌표·색상은 RedisJSON 저장과 새 참여자의 로딩에서 일치했습니다.

프런트엔드 150개 테스트, 브로커 권한·Room·TLS 전송 관련 25개 테스트가 통과했습니다. [재현 결과](canvas-broker-membership-recovery-results.json).

검증용 임시 캔버스 #2038은 연결 종료와 캐시 해제 후 정상 API로 삭제했습니다. 임시 인증 파일도 제거했습니다.
