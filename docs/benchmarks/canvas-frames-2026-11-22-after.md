## 요약

- **값 선택(`<select>`)이 있는 객체:** 대체 버튼으로 바꾸자 이동 중 레이아웃이 사라졌다. 혼합 캔버스 이동에서 레이아웃 실행 170회 → 5회, 다시 그리기 344회 → 19회, 레이아웃 시간 101ms → 2ms, 이동 작업 2261ms → 1277ms가 됐다. CPU 4배 감속 이동 지연 프레임은 16.1% → 8.9%다.
- **확대·축소 중 DOM 제거·재생성:** 혼합 캔버스 확대·축소에서 `removeChild` 519ms → 109ms, 이미지 맞춤 강제 레이아웃 188ms → JS 상위 5위 밖, 확대·축소 작업 949ms → 714ms, 지연 프레임 2% → 0.3%다.
- **깊이 240개:** 불러온 직후 JS 힙이 108MB → 27MB, 확대·축소 작업이 670ms → 529ms다.
- **일반 CPU 스크롤 지연 프레임:** 모든 시나리오에서 0~1.4%로, 대부분 0%다.
- **남은 비용:** 카메라 적용, Chrome Layerize, 고급 스타일·흐름 연결선의 확대·축소 지연(3.5% 안팎)은 그대로다.
- **같이 고친 것:** 1600% 확대에서 글자·선이 흐려지던 문제, 촘촘한 격자, VM CLI 에이전트 제거(API 키 방식으로 일원화), YouTube 임베드 규정·오픈소스 고지 정리.

### 2. DOM 객체 안의 기본 `<select>` → 정적 대체 버튼

- **변경:** 캔버스 객체 안의 기본 `<select>`를 모두 `CanvasSelect`로 바꿨다. 평소에는 같은 모양의 버튼만 그리고, 포인터가 올라가거나 키보드 포커스가 들어올 때만 실제 `<select>`를 마운트한다. 터치는 첫 탭에서 `<select>`로 바꾸고 바로 연다.
  - 대상: `ValueObject`(2), `CanvasAgentNode`(2), `CanvasAgentInputNode`, `CanvasAgentOutputNode`, `CanvasAgentRouterNode`, `CanvasAgentOrchestratorNode`(2), `QuestionCard`, `ProjectObject`(9)
  - `CanvasSelect`는 대체 버튼에도 `data-*`, `aria-*`, `style`, 포인터 핸들러를 넘긴다. `data-object-action`처럼 캔버스 드래그를 막는 속성이 빠지지 않게 하기 위해서다. `multiple`·`size` 같은 `<select>` 전용 속성만 뺀다.
  - 스타일 선택자에 `.canvas-select-proxy`를 추가했다(`question-card.css`, `projects.css`, `canvas-multi-agent.css`, `object-styling.css`, `value-object.css`).

### 3. 확대·축소 중 DOM 객체 제거·재생성 → 렌더 창을 벗어난 객체를 2초 유지

- **변경 (`src/pages/CanvasPage.jsx`):** 렌더 창을 벗어난 DOM 렌더 객체를 바로 지우지 않고 2초 동안 유지한다(최대 96개). 확대했다가 곧 축소하면 같은 DOM을 다시 쓴다. 유지 시간이 끝나는 시점에 한 번 다시 계산한다.
  - 처음에는 벡터 객체(도형·연결선·드로잉·텍스트)도 유지했다. 그러자 공간 질의의 변경분 경로를 쓰지 못해 `shapes-240`의 확대·축소 지연이 2.8/1.7/4.3%에서 5.2/5.1/4.4%로 나빠졌다. 그래서 DOM으로 그리는 종류만 유지하도록 고쳤다.
- **변경 (`src/canvas/CanvasImageContent.jsx`):** 이미지 맞춤 계산에서 `clientWidth`를 읽던 것을 `ResizeObserver`의 `contentRect`로 바꿨다. 마운트 직후 즉시 호출하던 `fit()`도 없앴다. 강제 레이아웃이 사라진다.

### 4. 축 눈금 SVG의 재생성 → 확대·축소가 멈출 때까지 SVG 갱신 보류

- **변경 (`src/canvas/CanvasAxisTicks.jsx`):** 카메라 움직임이 끝난 뒤 180ms 안에 다시 움직이면 빠른 캔버스 눈금을 계속 쓴다. SVG 눈금은 조용한 시간이 지난 뒤에 한 번만 다시 그린다. 확대·축소 단계마다 텍스트 노드를 지우고 만드는 일이 없어진다.
- **변경 (`src/canvas/canvas-grid.css`):** `.canvas-stage:has(> .canvas-grid-surface)`를 `.canvas-app-page .canvas-stage { background-image: none; }`로 바꿨다. 무대는 항상 격자 면을 렌더하므로 `:has()` 검사가 필요 없었다. 축 눈금 변경 때마다 다시 평가되던 `:has()` 무효화 하나가 사라진다.

### 8. 객체마다 다른 깊이 → 스냅샷 버킷 지연 생성

- **변경 (`src/canvas/itemSnapshots.js`):** 스냅샷을 만들 때 해시 버킷 1024개를 미리 만들지 않는다. 처음 쓰는 버킷만 만든다. 깊이 240개에서 비어 있는 스냅샷 480개가 각각 버킷 1024개를 들고 있던 것이 원인이었다.

- **1. 카메라 이동의 기본 비용:** `apply()`, 축 눈금 빠른 그리기, GPU 워커 투영, Chrome Layerize는 그대로다. JS로 transform을 바꾸는 구조에서는 Layerize를 피할 수 없다.
- **5. 고급 스타일 객체:** 합성 레이어 수를 줄이려면 시각 결과가 바뀐다.

## 같은 작업에서 고친 화면 문제

측정 후 사용자 확인 과정에서 나온 두 가지다. 측정 결과(아래 표)는 이 수정이 들어간 빌드에서 다시 잰 값이다.

### 1600% 확대에서 글자·선이 흐려짐

- **원인:** 벡터·텍스트 객체의 래스터 배율 상한이 4였다(`src/canvas/graphicsQuality.js`의 `maxRasterRatio: 4`, 확대 배율도 4로 잘림). 1600%에서는 4배로 그린 그림을 다시 4배로 늘려 보여 줬다.
- **변경:**
  - 상한을 32(DPR 2 × 1600%)로 올리고, 확대 배율은 최대 확대 배율(`MAX_CANVAS_SCALE`)까지 반영한다.
  - 큰 객체가 그 배율로 전체를 그리면 텍스처가 커진다. 그래서 전체 크기로 그리면 목표 배율의 60% 아래로 떨어지는 객체는 화면에 보이는 영역(여백 15%)만 잘라 최대 4M 픽셀로 그린다(`src/canvas/DepthVectorLayer.jsx`). 원래 연결선에만 쓰던 방식을 모든 래스터 객체로 넓혔다. 연결선이 아닌 객체는 화면이 객체 넓이의 절반보다 작을 때만 자른다. 그래야 이동할 때 다시 그리는 횟수가 늘지 않는다.
- **확인:** 1800×1100 화면에서 240×60px 텍스트를 1600%로 확대해 스크린숏으로 비교했다. 글자 가장자리의 번짐이 사라졌다.

### 격자가 너무 촘촘함

- **원인:** 격자 표시 간격을 맞춤 간격(기본 1 캔버스 픽셀)에서 바로 계산했다. 그래서 화면 간격이 확대 배율과 상관없이 28~56px(그 전 버전은 12~24px)에 머물렀다. 1600%에서도 32px 간격의 점이 화면을 덮었다.
- **변경 (`src/canvas/gridProjection.js`, `canvas-grid.css`):** 처음 격자 규칙으로 되돌렸다.
  - 20 캔버스 픽셀(맞춤 간격이 더 크면 그 배수)마다 점을 찍고, 화면에서 12px보다 촘촘해질 때만 두 배씩 늘린다. 100%에서 20px, 1600%에서 320px이다.
  - 점은 반지름 1px에 0.5px의 부드러운 가장자리로, 처음 격자와 같다.
  - 카메라를 따라 움직이는 방식은 지금 것을 유지한다. 미리 그린 면을 한 주기 안에서 옮기고, 면 크기를 "화면 + 한 주기"로 맞춘다. 간격이 512px를 넘을 때만 배경 위치로 옮긴다.

- 표 8의 확대·축소에서는 `removeChild` 대신 `insertBefore`가 173ms 나온다. 유지했던 객체가 렌더 창으로 돌아올 때 DOM 순서를 맞추느라 다시 끼워 넣는 비용이다. 완화하지 않았다.
- 축 눈금 SVG 갱신은 완화 후 빌드에서 압축 이름 `o0`(눈금 값이 같은 텍스트 노드를 다시 쓰는 함수)로 나타난다. 확대·축소를 멈출 때마다 한 번씩 실행되므로 없어지지는 않고 절반으로 줄었다.
- 축 눈금 SVG 갱신을 미뤄도 확대·축소 중 레이아웃 실행 수(38~43회)는 거의 그대로다. 빠른 캔버스 눈금과 다른 객체의 레이아웃이 남아 있기 때문이다.
- 이동 단계의 카메라 적용(`useCanvasCamera` `apply()`, 65~77ms), Layerize, GPU 워커 투영은 완화 전후가 같다.

### 확대·축소 작업 시간 증가와 추가 수정

위 CPU 4배 감속 결과에서 여러 시나리오의 확대·축소 작업 시간이 100~300ms 늘었다(빈 캔버스 1230 → 1337ms, 드로잉 8 1105 → 1414ms). 원인은 격자를 처음 규칙으로 되돌리면서 격자 면의 크기(`width`/`height`)를 간격에 맞춰 매 프레임 바꾼 것이다. 확대·축소 중에는 간격이 매 프레임 달라지므로 프레임마다 레이아웃이 추가됐다.

면 크기를 2의 거듭제곱 단위로 올려 잡아, 간격이 그 단위를 넘을 때만 바뀌게 했다(`applyGridProjection`). 수정 후 늘어났던 시나리오만 다시 쟀다([canvas-frames-2026-11-22-after-cpu4x-grid.json](canvas-frames-2026-11-22-after-cpu4x-grid.json), 2회 중앙값).
