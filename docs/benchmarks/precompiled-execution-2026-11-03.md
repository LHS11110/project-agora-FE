# 사전 빌드 실행 성능 비교 — 2026-11-03

현재 운영 런타임과 동일한 게스트 이미지의 별도 테스트 VM에서 측정했다. 기존 사용자 VM은 종료하거나 변경하지 않았다.

## 조건

- 호스트: Intel Core i5-12400F, Linux/KVM. 다른 서비스와 호스트를 공유하므로 전용 장비의 보편적인 성능 수치가 아니다.
- VM: small, 1 vCPU, RAM 1 GiB, 워커 메모리 제한 768 MiB.
- 케이스별 3회 독립 라운드. 매 라운드 각 모드의 첫 실행을 측정하고 같은 코드를 8회 추가 실행했다. 모드 순서는 라운드마다 교대했다.
- 모드/라운드마다 언어 환경을 초기화했다. 사전 빌드는 라운드별 소스를 달리해 기존 결과물의 캐시 적중을 배제했다.
- 빌드·첫 실행은 3개 표본, 반복 실행은 24개 표본의 중앙값이다. 원본 JSON에는 개별 표본, 평균, 표본 p95도 포함한다. 이 표본 수로 서비스 SLA를 추정하지 않는다.
- 호스트 런타임 매니저의 요청 전송부터 VM 실행 및 출력 수신까지의 경과 시간이다. HTTP 인증, 외부 네트워크, 브로커, 브라우저 렌더링은 포함하지 않는다.
- 모든 실행은 0부터 99,999까지 더해 `4999950000`을 출력하며 응답·종료 코드·출력을 검증했다. 큰 소스는 동일 연산에 호출하지 않는 함수/메서드 300개를 추가해 파싱/컴파일 부담을 비교한다.
- 동일 엔진·기본 최적화 옵션을 사용했다. C/C++은 -O0이다. 기존 모드는 실행 환경을 유지하고 사전 빌드 모드는 매번 독립 프로그램을 시작한다. 이러한 실제 제품 동작의 차이를 포함하는 비교다.
- VM 생성 및 최초 Python 요청 8885.8 ms는 아래 언어 비교에서 제외했다.

## 해석

- 기존 C/C++ Clang 워커도 동일 소스의 JIT 결과를 메모리에 캐시한다. 기존 GCC 워커도 바이너리를 디스크에 캐시한다. 기존 실행이 매번 처음부터 컴파일하는 구조가 아니므로 반복 실행에서 AOT의 큰 우위가 보장되지 않는다.
- Python은 기존 인터프리터 유지 비용과 새 인터프리터 시작 비용의 차이가 바이트코드 준비 절감보다 클 수 있다.
- JavaScript 사전 빌드는 V8 코드 캐시다. Node 프로세스/컨텍스트 시작과 실행 중 JIT 비용은 여전히 발생한다.
- Java 기존 모드는 JShell로 클래스 정의를 평가하고 main을 호출한다. 사전 빌드 모드는 javac 결과를 새 JVM에서 실행한다. JVM 시작 비용까지 포함해 비교해야 한다.
- Shell은 컴파일하지 않는다. 사전 구문 검사로 준비 여부를 검증하고 별도 Bash 프로세스로 실행한다.
- 빌드 전 완료 여부를 보장하고 결과물을 재사용하는 기능과, 반복 실행의 최저 지연은 다른 목표다. 사전 빌드가 모든 언어에서 빨라지는 것으로 해석하면 안 된다.
