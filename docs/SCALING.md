# 동시 사용과 과부하 처리

## 현재 적용한 처리 한도

- C++ 캔버스 저장 큐: 완료되지 않은 요청 최대 1,024개, 대기 중 JSON 데이터 최대 64 MiB. 실행 중 작업은 바이트 한도에서 제외됩니다. 초과 요청에는 기존 저장 실패 응답을 반환하며 접수한 작업과 barrier 순서는 유지합니다.
- C++ WebSocket: 연결별 출력 버퍼 최대 16 MiB. 한도를 초과하는 연결은 종료해 재연결 및 최신 상태 동기화를 유도합니다.
- 클라이언트 호스트: 대기 요청 최대 256개 또는 직렬화한 작업 데이터 32 MiB. 같은 요청의 재전송은 대기열을 중복 점유하지 않습니다.
- 호스트 승인 처리: 한 주기에서 최대 32개 요청을 처리하고, 요청 사이에 8 ms 시간 예산을 확인합니다. 단일 요청의 처리 시간 자체를 선점하지는 않습니다.
- 브로드캐스트 변경 로그: 256개 또는 64 MiB에 도달하면 새 승인을 보류합니다. 승인 한 건 때문에 바이트 한도를 일시적으로 초과할 수 있습니다. 전송이 회복되면 보류한 요청을 순서대로 처리합니다. 변경 내역을 삭제해서 한도를 맞추지는 않습니다.
- 서버 저장 전송: WebSocket 버퍼가 4 MiB 이상이거나 성공 응답 대기 배치가 8개 이상이면 새 저장 배치를 보류합니다.
- P2P 데이터 큐: 앞에서 배열을 반복 이동시키지 않고 인덱스로 진행하며 보낸 참조를 즉시 해제합니다. 주기적으로 배열을 압축합니다.
- 마우스·레이저: 직접 P2P 채널에서 전송합니다. 출력 버퍼가 128 KiB 이상이면 오래된 위치를 쌓는 대신 해당 업데이트를 생략합니다.

요청 카운트, 승인 응답 후 다음 요청 전송, 호스트 교체 시 변경 큐 유지, 초기 동기화 대기, TLS 통신은 기존 규칙을 유지합니다. 로컬 오프라인 편집 큐와 전체 문서 크기에는 이번 변경으로 제한을 추가하지 않았습니다.

## 검증 범위

클라이언트 테스트는 중복 요청 1,000회, 전달 지연 상태에서 편집 300회 후 회복, 느린 포인터 채널, 승인·권한·호스트 교체·부분 전송을 확인합니다. 서버 테스트는 저장 큐 1,024개 포화 후 거절, barrier 유지 및 공간 확보 후 순서대로 처리하는 동작을 확인합니다. 실제 동시 접속 부하 테스트로 수용 인원을 측정한 결과는 아닙니다.

## 배포 규모의 제한

서로 다른 캔버스는 별도의 호스트와 C++ 할당을 사용하지만, 캔버스 하나의 영구 객체 변경은 단일 브라우저 호스트가 승인합니다. 마우스·레이저·음성 연결은 전체 P2P 구조이므로 참여자 수에 따라 전체 연결 수가 제곱으로 증가합니다. 수백 명이 같은 캔버스에서 음성까지 사용하는 목표에는 SFU나 별도 presence 릴레이, 캔버스 할당과 서버 수 확장, 실제 부하 측정이 추가로 필요합니다.

화면은 기존 공간 인덱스로 보이는 객체만 렌더링하며, 편집자 목록은 객체별로 묶어 반복 검색을 줄였습니다. 문서 변경 시 공간 인덱스를 재구축하고 전체 상태를 병합하는 비용은 남아 있습니다. 객체 수만 개 목표에는 변경 객체 중심 인덱스 갱신과 스냅샷 분할을 별도로 측정해야 합니다.

저장 큐와 출력 버퍼 한도는 메모리 보호 수단이며 처리량을 보장하는 수치가 아닙니다. 운영에서는 캔버스 수, 요청 크기, 큐 거절, 저장 지연, 연결 종료와 브라우저 프레임 시간을 함께 측정해야 합니다.
