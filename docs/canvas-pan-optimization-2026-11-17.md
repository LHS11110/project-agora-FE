# 캔버스 이동 최적화

## 원인

- 이동 시 양자화된 화면 경계가 바뀔 때마다 공간 검색과 표시 목록 비교가 반복됐다. 객체가 화면에서 제외되면 SceneViewModel과 래스터 준비 목록을 다시 구성하여 긴 프레임이 발생했다.
- 이동 중 90ms마다 큰 React 페이지를 갱신했다.
- 개발 StrictMode 정리 시 취소된 requestAnimationFrame ID가 남아 다음 예약을 차단했다. 기존 성능 테스트는 실제 이동을 검증하지 않아 이를 놓쳤다. 이전 문서의 확대·축소 수치를 정정했다.

## 변경

- 화면 주변 준비 영역을 2개 셀(축소 단계에 따라 화면 기준 최소 약 512px)로 확보한다. 실제 화면과 64px 여유 영역이 그 안에 있으면 이동 중 표시 목록을 재사용한다.
- 준비 영역을 벗어나거나 데이터·공간 인덱스·편집 대상이 변경되면 다시 검색한다. 이동 종료 시에도 현재 화면에 맞게 갱신한다.
- 픽셀 이동은 계속 매 프레임 처리한다. React 갱신은 느린 이동 시 최대 240ms 간격, 빠른 이동은 이전 갱신 지점에서 256px 이동 시 수행한다.
- 정리 시 카메라 예약 ID와 크기 관찰 상태를 초기화하여 재설정 이후에도 이동이 계속되도록 했다.
- 성능 테스트에 중간 버튼 실제 드래그와 카메라 이벤트 수 검증을 추가했다.

## 측정

Chrome 개발 빌드, 2100×1450, 모의 브로커, 코드 객체 100000개와 보조 객체 1개. 120회 포인터 이동, 가로 ±800px·세로 ±250px 왕복 경로. 작은 객체에는 기존 개요 렌더링이 적용된다.

| 지표 | 실제 이동 검증 후 수정 전 | 최종 수정 후 |
|---|---:|---:|
| 평균 FPS | 33.7 | 50.0 |
| 프레임 간격 p95 | 50.1ms | 33.4ms |
| 최대 프레임 간격 | 383.4ms | 50.1ms |

수정 전은 카메라 예약 결함만 먼저 수정한 상태에서 측정했다. 최종 테스트에서는 실제 카메라 이벤트 129회와 좌표 변경을 확인했고 브라우저 예외가 없었다. 환경과 서버 부하가 달라질 수 있는 단일 실행 결과이며 60FPS 보장은 아니다. 모든 코드 편집기가 활성화된 부하나 동영상 동시 재생 성능을 뜻하지 않는다.

## 검증

- 카메라 갱신 간격, 빠른 이동, 준비 영역 경계·축소·이동 방향, 공간 인덱스, 공동 편집, 포인터 관련 테스트 34개 통과.
- 두 브라우저의 실제 카메라 변환, 관전 화면 중심·배율 일치 및 누락 이벤트 복구 테스트 통과.
