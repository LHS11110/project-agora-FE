# 대용량 캔버스 연결 안정성

2026-10-15, Project Orchestra를 통해 Spring·C++·Phoenix broker·정적 프런트엔드를 배포했다.

## 확인한 원인과 변경

- **활성 캔버스 접속 실패:** Spring 인증·설정 API가 RedisJSON의 전체 문서를 읽었다. 객체 데이터가 16MB를 넘으면 Redis 응답 제한에 걸려 HTTP 500이 발생했다. 현재는 비밀번호·멤버·그룹·revision 등 메타데이터만 JSONPath로 조회한다. 최신 Redis 상태와 기존 권한 검사는 유지한다.
- **공유 백엔드 연결 종료:** C++는 16MB 초과 응답에서 브로커 공유 WebSocket을 닫았다. 현재는 응답을 128KB WebSocket 프레임으로 나누고 drain에 따라 이어 보낸다. 전송 대기 중 요청도 유지하며, 과부하는 해당 요청에 오류로 응답한다. 내부 논리 응답은 128MB, 대기 응답은 총 256MB로 제한한다. 대용량 초기 연결 요청은 동시에 최대 2개만 처리한다.
- **과도한 메시지:** 호스트 준비 메시지가 참가자마다 초당 약 30회 전송됐다. 등록 전에는 1초, 등록 후에는 5초 간격으로 줄였다. 상태 요청도 500ms 간격으로 제한한다. 클라이언트 전송은 지난 1초의 180개 제한을 적용하며 커서 등 일시적 메시지는 140개에서 양보한다.
- **느린 수신자:** 객체 상태는 약 256KB 묶음으로 나눈다. 지원하는 참가자끼리는 최대 4개의 미확인 묶음만 전송하고 ACK가 오면 이어 보낸다. 막힌 ACK도 보존·재시도한다. 분할 계획은 재사용하고 전체 수신 전에는 상태를 적용하지 않는다. 단일 대형 객체는 묶음 목표 크기를 넘을 수 있다.
- **저장 응답 대기와 잘못된 중단:** 저장 거절에도 요청 ID를 포함하고, 확실한 혼잡 거절은 최신 저장 상태를 덮어쓰지 않고 재시도한다. 호스트 교체 후의 오래된 오류가 새 세션을 중단시키지 않도록 저장 요청과 term을 확인한다. 결과가 불명확한 저장 실패는 계속 별도로 처리한다.
- **초기 실패·유휴 종료:** 일시적인 HTTP 5xx·429·네트워크 오류와 첫 WebSocket 실패도 지수 backoff로 재연결한다. 인증·권한·없는 캔버스 오류는 재시도를 중단한다. 브로커는 20초마다 WebSocket ping을 보낸다. RTC 바인딩용 연결에서는 객체 목록을 중복 전송하지 않는다.

## 검증

- 프런트엔드 Node 테스트 118개 통과: 전송량 제한, 막힌 ACK 재시도, 부분 상태의 원자적 적용, 분할 계획 재사용, 준비 메시지 빈도, 누락 감지와 재동기화, 저장 재시도 시 최신 변경 보존, 초기 API 재시도 정책 및 기존 협업 회귀 테스트.
- Phoenix·실제 C++ TLS 통합 테스트 25개 통과. 20MB 응답 후 같은 Gun/WebSocket으로 후속 요청을 처리했고, 40개 동시 질의·TLS 1.3·인증·ACK 역할 제한도 확인했다.
- Spring 메타데이터·Sentinel failover 테스트 3개 통과. 20MB 객체 문서에서도 메타데이터 응답은 16KB 미만이며 비밀번호·멤버·revision이 유지된다. 별도 환경을 요구하는 TLS Sentinel smoke 테스트 1개는 제외했다.

객체 수 자체보다 실제 직렬화된 데이터 크기와 수신 속도가 중요하다. 이 변경은 무제한 메시지 크기나 모든 네트워크에서의 무중단을 보장하지 않는다. 이전 프런트엔드 세션에는 새로고침이 필요하다.

실제 배포 주소에서 테스트 이미지 객체 100개(화면 밖에 배치한 반복 데이터)의 저장과 20,021,894바이트 초기 스냅샷을 확인했다. 두 클라이언트의 상태 묶음과 ACK는 각각 100개 처리됐고, 네 WebSocket은 입력 없이 70초 동안 종료되지 않았다. 초기 설정 API의 503과 첫 WebSocket 접속의 1013 종료를 주입한 뒤 자동 재접속과 최신 100개 객체 동기화도 통과했다. 두 클라이언트를 같은 headless 브라우저에서 실행하므로 인위적인 배경 타이머 제한은 해제했다. 이는 통신 검증이며 이미지 렌더링 성능 측정은 아니다.
